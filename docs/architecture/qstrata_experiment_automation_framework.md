## 1. Purpose

The QStrata research program completed its binary benchmarking phase (Q17–Q29) through manual, sequential experiment execution. Each experiment was individually scripted, individually run, and individually reported. This approach was appropriate for the binary phase, where the number of experiments was small and the configurations were fixed by the scientific design rather than generated by a search procedure.

The NAS, multiclass, and optimization phases will not have this property. Classical NAS (Q32) will generate tens to hundreds of trial configurations. Quantum NAS (Q33) will generate further search trials across DV and CV head spaces. Multi-objective NAS (Q34) will run trials simultaneously across AUROC, F1, parameter count, latency, and stability objectives. Multiclass benchmarking will replicate the binary protocol across a significantly expanded task space.

Manual execution does not scale to this regime. Without automation:
- Configuration drift between experiments is unavoidable
- Metric collection is inconsistent across runs
- Failed runs are silently lost or incomplete
- Results cannot be traced back to exact code states
- Leaderboard aggregation across trials is impractical
- Reproducibility cannot be guaranteed

Automation is required before NAS begins. A reproducible runner must exist before any search generates trial configs. Orchestration must precede distributed scaling. These are not preferences — they are sequencing constraints enforced by the roadmap gating structure.

**Q30 defines the architecture only. Implementation begins in Q31.**

## 2. Design Philosophy

Five principles govern all architectural decisions in the QStrata experiment automation framework.

### Experiment-Centric Architecture

The experiment is the primary unit of organization. Every config, metric, artifact, log, checkpoint, and leaderboard entry is organized around an `experiment_id`. There is no global state that cannot be reconstructed from the per-experiment records. An experiment is a self-contained, independently reproducible unit of scientific work.

This principle prevents the most common source of research data loss: implicit shared state between runs that makes individual experiments uninterpretable in isolation.

### Reproducibility-First

Every experiment must be fully reconstructable from two things only: its frozen configuration file and the `git_commit` SHA recorded at run start. Nothing outside those two artifacts should be required to reproduce the experiment's behavior. Environment-variable overrides, implicit defaults, and undocumented runtime parameters are prohibited. Config freezing is enforced mechanically — not by convention.

### Local-First Execution

Local GPU workflows are validated before any distributed infrastructure is introduced. AWS and Ray are scaling layers, not science layers. Distributing an unvalidated workflow amplifies its problems rather than solving them. The local runner (Q31) must demonstrate stability, reproducibility, and metric completeness before Q35 designs distributed extensions.

### Failure Tolerance

Interrupted and crashed runs must be recoverable without data loss. A framework that silently discards partial results incentivizes researchers to never interrupt long runs, which prevents timely error detection. Partial run state — checkpoint, partial metrics, stdout log — must be preserved on abnormal exit and must be sufficient to resume from the point of interruption.

### NAS Compatibility

The framework must accommodate classical NAS (Q32), DV quantum NAS (Q33), and CV quantum NAS (Q33) without architectural redesign. NAS trial generation produces valid experiment configs. The runner executes them identically to hand-crafted experiments. The framework does not need to know whether a config was generated by a human or a search algorithm. This is enforced by making the config schema search-space agnostic — the `model.parameters` block accommodates any key-value set that varies between trials.

## 3. Experiment Lifecycle

An experiment passes through the following states. Each state transition must be logged with a timestamp.

| State | Description |
|---|---|
| `queued` | Experiment defined; config frozen; waiting for execution slot in the runner queue |
| `running` | Actively executing on local GPU; metrics accumulating per epoch; stdout captured |
| `completed` | Finished successfully; all metrics exported; artifacts saved; checkpoint saved |
| `failed` | Terminated with unhandled exception; failure log captured; partial state preserved |
| `interrupted` | Stopped externally (SIGINT, OOM, hardware failure); last valid checkpoint preserved; partial metrics preserved |
| `resumed` | Restarted from last valid checkpoint after interruption; metrics accumulated before interruption retained |
| `archived` | Closed experiment; record is immutable; no further modification permitted |

**State transitions:**

```
queued → running → completed → archived
                → failed → archived
                → interrupted → resumed → completed → archived
                                        → failed → archived
```

All terminal states (`completed`, `failed`) transition to `archived` after metrics and artifacts are finalized. An experiment in `archived` state has an immutable record — its metrics cannot be retroactively altered, and its config cannot be modified.

The `interrupted` state must be set synchronously on receipt of SIGINT or OOM signal — before the process exits. This is enforced by a signal handler registered at run start that writes `status: interrupted` to the experiment metadata file before allowing the process to terminate.

## 4. Experiment Directory Structure

All experiment artifacts are organized under a single root directory:

```
experiments/
  configs/        frozen YAML configs; immutable once experiment starts
  results/        exported metrics, leaderboard entries, summary files
  logs/           per-experiment training logs, stdout captures
  artifacts/      model outputs, confusion matrices, plots
  leaderboards/   ranked result tables across experiments
  checkpoints/    best and final model checkpoints per experiment
```

**`configs/`** — Frozen YAML configurations. Each experiment's config is copied here at run start and set to read-only (`chmod 444`). This directory is the immutable record of what was intended to run. Any discrepancy between a config in this directory and a result in `results/` is a reproducibility violation.

**`results/`** — JSON metric exports. One file per experiment: `<experiment_id>.json`. Written at experiment end. Partial metrics (per-epoch values) written at each epoch to `<experiment_id>_partial.json` during training; this file is promoted to the final JSON on completion.

**`logs/`** — Continuous stdout/stderr captures. One file per experiment: `<experiment_id>.log`. Written continuously from process start to end. Retained for all lifecycle states, including `failed` and `interrupted`. The log is the primary diagnostic tool for non-reproducible failures.

**`artifacts/`** — Secondary outputs: confusion matrices, ROC curves, per-epoch plots, intermediate analysis files. Not required for reproducibility but useful for scientific interpretation. Organized under `<experiment_id>/` subdirectory.

**`leaderboards/`** — Cross-experiment ranked tables. One CSV per phase (e.g. `binary_dv.csv`, `classical_nas.csv`). Automatically regenerated after each experiment in the phase completes. Ranked by primary metric (configurable per phase). Leaderboard entries reference `experiment_id` only — no free-form metric descriptions.

**`checkpoints/`** — Model checkpoints associated with experiments. Organized under `<experiment_id>/` subdirectory. Contains `best.pt` (checkpoint at best validation metric) and `final.pt` (checkpoint at last epoch). Linked to the experiment record by `experiment_id`. Not committed to the repository (covered by `.gitignore`).

**Config immutability rule:** A config in `experiments/configs/` is frozen at the moment it is copied there (experiment start). No modification to a running or archived experiment's frozen config is permitted. Any modification constitutes a reproducibility violation and invalidates the experiment record. If a config needs to change, a new experiment with a new `experiment_id` must be created.

## 5. Experiment Metadata Standard

Every experiment must record the following metadata fields. This record is written to `experiments/results/<experiment_id>.json`.

| Field | Description |
|---|---|
| `experiment_id` | Unique identifier — format: `<ISO_timestamp>_<8char_hash>`, e.g. `20260526T143021_a3f7c2b1` |
| `timestamp` | ISO 8601 start time, e.g. `2026-05-26T14:30:21+00:00` |
| `dataset` | Dataset name and version string, e.g. `vindr_binary_roi_224_v1` |
| `model` | Architecture identifier string, e.g. `dv_hybrid_c006d040_4qubit` |
| `seed` | Integer random seed used for all RNG initialization |
| `hardware` | Dict: GPU model, CUDA version, CPU fallback flag, available memory |
| `git_commit` | Full 40-character SHA from `git rev-parse HEAD` at run start; `dirty` if working tree has uncommitted changes |
| `metrics` | Dict mapping metric name to value for all tracked metrics |
| `runtime` | Wall time in seconds from run start to experiment end (all states) |
| `status` | Final lifecycle state string from the seven defined states |

These ten fields are mandatory. An experiment record missing any of these fields is incomplete and must not be added to any leaderboard.

## 6. Artifact Management

### Config Freezing

At experiment start, before any data loading or model initialization:
1. Config YAML is validated against the schema
2. Validated config is copied to `experiments/configs/<experiment_id>.yaml`
3. File permissions set to read-only: `chmod 444 experiments/configs/<experiment_id>.yaml`
4. Config hash (SHA-256) is recorded in the experiment metadata
5. Any subsequent attempt to write to the frozen config file raises an error

This sequence must complete before the runner proceeds to any other operation.

### Metric Exports

Two types of metric exports:

- **Partial metrics** (`<experiment_id>_partial.json`): written at the end of each training epoch. Contains all metrics computed so far. Used for interrupted run recovery and real-time monitoring.
- **Final metrics** (`<experiment_id>.json`): written on experiment completion (state `completed` or `failed`). Includes all epoch-level metrics plus final test evaluation. This file is immutable once written.

### Leaderboard Generation

After each experiment reaches `archived` state:
1. Phase leaderboard CSV is read from `experiments/leaderboards/<phase>.csv`
2. New experiment's metrics are appended
3. Leaderboard is re-sorted by the phase's primary metric (configurable)
4. Updated CSV is written back

Leaderboard entries contain only: `experiment_id`, `timestamp`, `model`, `seed`, and all tracked metrics. No free-form text. All comparisons between experiments are performed by joining on `experiment_id` with the frozen config records.

### Checkpoint Association

Each experiment owns its checkpoints under `experiments/checkpoints/<experiment_id>/`:
- `best.pt` — saved at the epoch with the best validation metric
- `final.pt` — saved at the last epoch (or last completed epoch if interrupted)

The experiment metadata record contains the full path to both checkpoints. Checkpoints are not committed to git (`.gitignore` rule). They are local artifacts linked to the experiment record.

### Experiment References

All reports and comparative analyses must cite `experiment_id` rather than free-form descriptions. "The best-performing model" is not a valid reference. "Experiment `20260526T143021_a3f7c2b1` (Q21 DV hybrid, seed 42)" is. This convention makes cross-report traceability mechanical rather than interpretive.

## 7. Multi-Objective Tracking

The framework must track all of the following per experiment. No experiment is considered complete until all tracked metrics are exported:

| Metric | Type | Rationale |
|---|---|---|
| `auroc` | Primary scientific | Rank-based, threshold-independent discriminative performance; primary comparison metric across all phases |
| `f1` | Primary scientific | Threshold-dependent, class-balance-aware; required for imbalanced datasets and clinical relevance |
| `parameter_count` | Efficiency | Trainable parameter count; model compactness; deployment constraint |
| `latency` | Efficiency | Inference latency in ms/sample; clinical deployment feasibility; measured over 100 single-sample passes |
| `numerical_stability` | Health | NaN/inf count across training; gradient norm health flags; covariance health flags for CV models |
| `runtime` | Operational | Wall-clock training time in seconds; resource cost tracking |
| `memory_usage` | Operational | Peak GPU and CPU memory in MB; informs hardware budget decisions |
| `generalization_gap` | Scientific | val_loss − train_loss at convergence; overfitting signal; stability indicator |

Single-metric optimization is prohibited by design. The framework does not expose a "primary metric" for optimization at the config level — all eight metrics are tracked equally, and any selection between them is a human scientific decision made after reviewing the full Pareto frontier.

## 8. Failure Recovery Design

Failure recovery is a first-class design concern, not an afterthought.

**Signal handler registration.** At run start, the runner registers handlers for SIGINT, SIGTERM, and SIGUSR1. On receipt of any of these signals, the handler:
1. Sets experiment status to `interrupted` in the metadata file (synchronous write)
2. Flushes partial metrics to `<experiment_id>_partial.json`
3. Saves current epoch checkpoint if a checkpoint has been computed this epoch
4. Logs the interruption event with timestamp
5. Allows the process to exit

This sequence is guaranteed to complete before the process exits, ensuring the partial state is always recoverable.

**Checkpoint granularity.** The runner saves a checkpoint at the end of every epoch (not just at the best epoch). On resumption, the runner reads the most recent checkpoint, restores the model state, optimizer state, and random state, and continues training from the next epoch. Metrics accumulated before the interruption are merged with the resumed run's metrics.

**Partial metrics preservation.** `<experiment_id>_partial.json` is written atomically at the end of each epoch (write to temp file, then rename). This ensures that even an OOM error mid-epoch does not corrupt the partial metric record from the previous epoch.

**Failed run traceability.** An experiment in `failed` state retains:
- The exception trace logged to `experiments/logs/<experiment_id>.log`
- The last known state (epoch number, best metric so far)
- The partial metric JSON up to the last completed epoch
- The checkpoint from the last completed epoch

Failed runs are not silently discarded. They are moved to `archived` state with `status: failed` and remain in the leaderboard with their partial metrics. This enables post-hoc diagnosis and manual resumption.

**Dirty working tree warning.** If `git rev-parse HEAD` shows a dirty working tree at run start, the runner logs a warning:
```
WARNING: Working tree is dirty. Experiment results may not be exactly reproducible.
git_commit: <SHA>-dirty
```
The experiment proceeds but the dirty flag is recorded. Experiments with `dirty` commits should not be added to published leaderboards.

## 9. NAS Compatibility

The framework is designed from the start to accommodate NAS trial generation from Q32 (classical feature extractor NAS), Q33 (DV and CV quantum head NAS), and Q34 (multi-objective NAS pilot) without architectural redesign.

**Config schema compatibility.** The experiment config schema (defined in `docs/specs/qstrata_experiment_config_schema.md`) includes a `model.parameters` block that accepts any key-value mapping. NAS trial generation varies this block. Classical NAS varies backbone parameters (channels, depth, block type). DV NAS varies head parameters (n_qubits, circuit_depth, ansatz_type). CV NAS varies head parameters (n_modes, cv_depth, squeezing_cap, encoding_scheme). The runner does not parse `model.parameters` — it passes the block to the model factory. No runner modification is needed to support new parameter search dimensions.

**Trial generation interface.** NAS search algorithms (Q32–Q34) produce lists of YAML dicts conforming to the experiment config schema. These are placed in the runner's queue directory. The runner picks them up and executes them identically to hand-crafted experiments. The runner does not know and does not need to know whether a config was generated by a human or a search algorithm.

**Leaderboard integration.** NAS trials are grouped under their search phase in the leaderboard directory (e.g. `classical_nas`, `dv_quantum_nas`). The leaderboard schema is identical to the binary benchmarking phase — same metric columns, same `experiment_id` reference structure. This allows direct cross-phase comparison.

## 10. Local-First Execution Principle

Local execution is not a temporary limitation before the "real" distributed work begins. It is a validation stage that cannot be skipped.

Local execution validates:
- That the experiment config schema is correct and sufficient
- That the runner's failure recovery actually works
- That multi-objective metrics are all computed correctly
- That leaderboards aggregate correctly across trials
- That reproducibility guarantees hold (same config + seed → same result)
- That NAS-generated configs are executable by the runner
- That the framework overhead does not dominate experiment runtime

None of these validations can be performed in a distributed setting. A bug in the runner that silently corrupts results will be harder to diagnose when running on 20 AWS instances than on a single local GPU.

**AWS and Ray are scaling layers, not science layers.** They remain blocked until:
- Q31 produces a local runner that passes all operational tests
- Q34 validates local NAS produces stable, reproducible results
- The distributed design (Q35) is explicitly approved before any cloud infrastructure is provisioned

Do not provision infrastructure to compensate for unvalidated experiments.

## 11. Scientific Integrity Protections

The automation framework enforces scientific integrity mechanically rather than by convention.

**Frozen configs prevent post-hoc modification.** Once an experiment starts, its config is read-only. It is impossible to modify a running experiment's hyperparameters without creating a new experiment with a new `experiment_id`. This prevents the most common form of "result massaging" — silently adjusting a parameter after observing the result.

**Seed locking ensures identical random state across reruns.** The runner sets all random seeds (Python `random`, `numpy`, `torch`) from the single `reproducibility.seed` value in the config, before any data loading or model initialization. This is the first operation performed by the runner. Any code that sets its own seed independently is a reproducibility violation.

**Git commit association guarantees code-experiment traceability.** Every experiment record contains the full `git_commit` SHA. Given an experiment ID, the exact code state that produced it is recoverable by `git checkout <SHA>`. Experiments run from dirty working trees are flagged but still recorded. Published results must reference a clean commit.

**Leaderboard entries are immutable once archived.** Archived experiment records cannot be modified. Leaderboard entries are derived from immutable records. A result that appeared in a leaderboard at time T cannot be altered retroactively. If a result is found to be erroneous, a corrected entry is added with a new experiment ID; the original entry is marked `status: retracted` but not deleted.

**No hidden hyperparameters.** All config values that affect results must appear in the frozen config. Default values for optional fields must be explicitly listed in the schema documentation, not silently assumed by the code. An experiment whose result cannot be reproduced from its frozen config alone has a hidden hyperparameter, which is a framework violation.

## 12. Future Infrastructure Transition

The framework is designed so each successive component extends — rather than replaces — the preceding one:

```
Q31 → local GPU runner implements this framework
      validates: config freezing, metric export, failure recovery, leaderboard generation
      gate cleared: Q32/Q33/Q34 may proceed

Q32 → classical NAS defines search spaces compatible with config schema
      varies: model.parameters (backbone architecture dimensions)
      gate cleared: Q33 (quantum NAS) may proceed after Q32 ceiling is known

Q33 → quantum NAS (DV/CV) extends search spaces within same framework
      varies: model.parameters (quantum head dimensions)
      same runner, same config schema, same leaderboard format

Q34 → local multi-objective NAS pilot runs trials through local runner
      no new infrastructure: Q31 runner + Q32/Q33 search spaces
      gate cleared: Q35 distributed design approved after Q34 validated

Q35 → distributed scaling design extends Q31 runner to AWS/Ray
      same config schema, same metric format, same leaderboard structure
      no science layer changes: only execution layer parallelized
```

At no transition point does the underlying config schema, metric format, or leaderboard structure change. Infrastructure layers extend the execution model without altering the scientific interface.
