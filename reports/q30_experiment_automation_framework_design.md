## 2. Why Automation Is Now Necessary

The binary benchmarking phase (Q17–Q29) used manual, sequential experiment execution. Each experiment was individually scripted, individually run, and individually reported. This approach was adequate for the binary phase for three reasons: the number of experiments was small (fewer than fifteen training runs), the configurations were fixed by the scientific design rather than generated by a search procedure, and the sequential nature of the phase meant that each experiment informed the next one before it was written.

The NAS, multiclass, and optimization phases will not have any of these properties. Classical NAS (Q32) will generate tens to hundreds of trial configurations across backbone architecture dimensions. Quantum NAS (Q33) will layer additional search dimensions across DV and CV head spaces. Multi-objective NAS (Q34) will execute multiple simultaneous optimizations across AUROC, F1, parameter count, latency, and stability objectives. Multiclass benchmarking will replicate the full binary experimental protocol across a significantly expanded task and label space.

At that scale, manual execution is not just inconvenient — it is scientifically unsound:

- **Config drift** between manually created experiments accumulates silently. A manually written experiment script for trial 47 of a NAS search will differ from trial 1 in ways that are not tracked.
- **Inconsistent metric collection** occurs when some runs export AUROC but not AUPRC, or when some runs measure latency and others do not.
- **Incomplete artifact retention** means that a crashed run loses its partial progress unless specific recovery procedures were anticipated in advance.
- **Non-reproducibility** is guaranteed when results cannot be traced to exact code states, exact seeds, and exact configurations.
- **No aggregation** means that comparing 50 NAS trial results requires manual assembly of metric tables, which introduces transcription errors.

Automation solves all of these problems by making the correct behavior the path of least resistance: configs are frozen automatically, metrics are exported automatically, failures are recovered automatically, and leaderboards are generated automatically.

## 3. Why Manual Experimentation No Longer Scales

The specific failure modes of manual experimentation at NAS scale are:

**Config drift.** When configurations are written by hand for each trial, small inconsistencies accumulate. Trial 1 uses `seed=42`; trial 17 was run at 2 AM and uses `seed=0` because the researcher forgot to set it. The leaderboard comparison between these trials is scientifically invalid, and there is no automated mechanism to detect this.

**Inconsistent metric collection.** Different experiment scripts written at different times collect different metrics. Some runs have latency measurements; others do not. Some have AUPRC; others report only AUROC. Comparative tables require either re-running experiments or reporting `—` for missing values.

**Incomplete artifact retention.** A training run that crashes at epoch 12 of 15 produces a partial checkpoint that may not be saved depending on whether the crash occurred before or after the epoch-end checkpoint save. Without systematic checkpoint-on-every-epoch, any crash produces an irrecoverable experiment.

**Non-traceable results.** A result table that says "model X achieved AUROC 0.71" is not reproducible if it does not record the exact script version, exact config, exact seed, and exact git commit. Informal record-keeping inevitably loses at least one of these.

**No leaderboard aggregation.** Comparing 50 NAS trials requires collecting 50 result files, extracting the same fields from each, and assembling a comparison table. This is 50 opportunities for transcription error.

**Difficulty tracing back to code.** When a result is surprising, determining whether it was produced by a bug requires knowing which code version ran. Without `git_commit` recording, this determination is impossible for experiments run more than a few days ago.

None of these failure modes occur at the scale of 12 binary baseline experiments. All of them become serious problems at the scale of 50+ NAS trials.

## 4. Framework Design Philosophy

The QStrata experiment automation framework is built on five principles:

**Experiment-centric architecture.** The experiment is the primary unit of organization. Every config, metric, artifact, log, checkpoint, and leaderboard entry is organized around an `experiment_id`. There is no global state that cannot be reconstructed from per-experiment records. Each experiment is self-contained and independently reproducible.

**Reproducibility-first.** Every experiment must be fully reconstructable from its frozen configuration file and the `git_commit` SHA recorded at run start. Nothing outside those two artifacts is required to reproduce the experiment's behavior. Config freezing is enforced mechanically — not by convention.

**Local-first execution.** Local GPU workflows are validated before any distributed infrastructure is introduced. AWS and Ray are scaling layers. They remain blocked until the local runner is validated and local NAS demonstrates stable results.

**Failure tolerance.** Interrupted and crashed runs must be recoverable without data loss. Partial run state — checkpoint, partial metrics, stdout log — is preserved on abnormal exit and is sufficient to resume from the point of interruption.

**NAS compatibility.** The framework accommodates classical NAS (Q32), DV quantum NAS (Q33), and CV quantum NAS (Q33) without architectural redesign. NAS trial generation produces valid experiment configs. The runner executes them identically to hand-crafted experiments.

## 5. Experiment Lifecycle Design

An experiment passes through seven defined states:

| State | Description |
|---|---|
| `queued` | Experiment defined; config frozen; waiting for execution slot |
| `running` | Actively executing; metrics accumulating per epoch; stdout captured |
| `completed` | Finished successfully; all metrics exported; artifacts saved |
| `failed` | Terminated with error; exception logged; partial state preserved |
| `interrupted` | Stopped externally (SIGINT, OOM); last checkpoint and partial metrics preserved |
| `resumed` | Restarted from last valid checkpoint; prior metrics retained |
| `archived` | Closed experiment; record is immutable; no further modification |

**State transition rules:**

```
queued → running → completed → archived
                → failed → archived
                → interrupted → resumed → completed → archived
                                        → failed → archived
```

The `interrupted` state must be set synchronously on signal receipt — before the process exits. This is enforced by a signal handler registered at run start. All terminal states transition to `archived` after finalization. `archived` experiments are immutable: their configs cannot be changed, their metrics cannot be altered, and their leaderboard entries are permanent.

## 6. Multi-Objective Experiment Tracking

Tracking AUROC alone is insufficient for scientific credibility and practical research decisions. A model that achieves AUROC 0.74 but requires 10× the training time, 5× the memory, and produces unstable predictions across seeds is not unconditionally superior to one achieving AUROC 0.71 with stable, compact, fast inference.

The framework tracks eight metrics per experiment. No experiment is considered complete until all eight are exported:

| Metric | Type | Scientific / Operational Relevance |
|---|---|---|
| `auroc` | Primary scientific | Rank-based, threshold-independent discriminative performance; primary comparison metric across all phases; stable to class imbalance |
| `f1` | Primary scientific | Class-balance-aware; computed at default threshold; captures precision-recall trade-off relevant to clinical decision support |
| `parameter_count` | Efficiency | Trainable parameter count; model compactness constraint; proxy for deployment feasibility and hardware cost |
| `latency` | Efficiency | Inference latency in ms/sample; clinical real-time constraint; measured over 100 single-sample passes to reduce variance |
| `numerical_stability` | Health | NaN/inf count across training; gradient norm health flags; covariance health flags for CV models; a model that passes AUROC but fails stability is not deployable |
| `runtime` | Operational | Wall-clock training time in seconds; informs budget planning for NAS searches; prevents infinite-runtime trials from occupying the runner |
| `memory_usage` | Operational | Peak GPU and CPU memory in MB; determines whether a trial is feasible on the target hardware without OOM; required for hardware budget planning |
| `generalization_gap` | Scientific | val_loss − train_loss at convergence; primary overfitting signal; required for compact model evaluation where the gap is expected to be small but must be confirmed |

Single-metric optimization is prohibited by design. The framework surfaces the full Pareto frontier. Selection between models is a human scientific decision informed by the complete metric set.

## 7. Failure Recovery Philosophy

Failure recovery is a first-class design concern:

**Interrupted runs are recoverable.** A signal handler registered at run start writes `status: interrupted` to the metadata file, flushes partial metrics, and saves a checkpoint before process exit. The last valid checkpoint from any epoch is sufficient to resume training.

**Failed runs are traceable.** An experiment in `failed` state retains its exception trace, partial metrics to the last completed epoch, and the last checkpoint. Failed experiments are not silently discarded — they are archived with `status: failed` and remain in the leaderboard with their partial records.

**Partial results are preserved.** Per-epoch partial metrics are written atomically (write to temp file, then rename) at the end of each epoch. A hardware failure mid-epoch cannot corrupt the previous epoch's record.

**No silent discard.** Every abnormal exit is logged with a timestamp and exception trace to `experiments/logs/<experiment_id>.log`. The log is the primary diagnostic tool for non-reproducible failures. An experiment whose failure cannot be diagnosed from its log has a framework violation.

## 8. Why AWS/Ray Remain Blocked

AWS and Ray are scaling mechanisms, not science mechanisms. Infrastructure does not replace scientific discipline. Distributing an unvalidated workflow amplifies its problems:

- A bug that silently corrupts metrics on a local GPU corrupts metrics on 20 AWS instances simultaneously
- A non-reproducible result that goes undetected locally goes undetected at scale, but is now embedded in 20× more experiment records
- A search procedure that is unstable locally cannot be stabilized by distributing it

AWS and Ray remain blocked until:
1. **Q31 produces a stable local runner** that passes reproducibility tests, failure recovery tests, and metric completeness tests
2. **Q34 validates local NAS** produces stable, reproducible results on a single GPU

Only after both conditions are satisfied does Q35 design the distributed scaling extension. No cloud infrastructure is provisioned before Q35's design is reviewed and approved.

This is a hard sequencing constraint, not a soft preference. The cost of premature cloud infrastructure is wasted money, wasted time, and a substantially more difficult debugging environment.

## 9. Relationship to Future NAS

The experiment automation framework is the direct prerequisite for all NAS work. The dependency chain is:

```
Q30 (this slice) → Q31 (local runner) → Q32 (classical NAS search)
                                      → Q33 (quantum NAS search)
                                      → Q34 (multi-objective NAS pilot)
                                      → Q35 (distributed scaling design)
```

**Q32 and Q33 produce experiment configs.** The config schema defined in `docs/specs/qstrata_experiment_config_schema.md` is the interface between NAS search algorithms and the runner. NAS trial generation varies `model.parameters` within a base config template. The runner executes the generated configs without modification.

**Q34 runs NAS trials through the Q31 runner.** There is no separate NAS execution engine. Q34 uses the same runner that Q31 implements, the same config schema that Q30 defines, and the same leaderboard format that Q30 specifies. Multi-objective optimization is achieved by running many trials through this infrastructure and applying selection criteria to the resulting leaderboard.

**NAS cannot proceed without a working runner.** Running NAS trials without a reproducible, failure-tolerant runner would produce results that cannot be verified, cannot be compared to other trials, and cannot be reproduced. The Q31 runner is not optional — it is the minimum necessary infrastructure for any NAS work.
